**Flagged for targeted verification:** RoleSeeder's manager permission `whereIn('module', [...])` list does
**not** include `task_calendar` or `calendar` module names for manager (only `member`/`client` get explicit
`task_calendar_view` etc.) — yet the module list includes `'calendar', 'task_calendar'` as *module* strings
which may or may not match actual `permissions.module` values in the DB. This is exactly the kind of
seeder/DB drift the CLAUDE.md warns about — verify by inspection whether Manager actually sees Calendar.

## Known dual-permission-system risk (from CLAUDE.md)

`HasPermissionChecks::checkPermission()` gives **blanket access to any `type === 'company'` user**, bypassing
Spatie entirely. The seeded `company@test.com` account is `type=company` (the "owner" role). Any controller
using `$this->authorizePermission()` should be probed for whether a *manager* (who is NOT `type=company`)
can be tricked into the same bypass, and conversely whether the owner's blanket access ever leaks into an
action that should still be workspace/company-scoped.

## Execution order

1. Superadmin — quick sanity pass (separate nav tree; company/plan/coupon/landing-page management).
2. Owner (`company@test.com`) — full nav baseline, since owner should see everything.
3. Manager — nav diff vs owner, dual-permission-bypass probe, Calendar visibility question above.
4. Member — nav diff, CRUD-own-scope checks (own timesheets/expenses/budgets view-only).
5. Client — nav diff, read-only enforcement, contract sign flow, task status via calendar only.
6. Cross-role: attempt forbidden direct-route access per role (403/redirect expected), cross-workspace
   record access (if a second workspace can be reached).
