## BUG-01 — Taxes page crashes to a blank error screen for every role that can see it

| | |
|---|---|
| **Severity / Priority** | Blocker / P0 |
| **Page / flow** | Finance → Taxes (`/taxes`) |
| **Roles affected** | Owner, Manager (both have `tax_view_any`) |
| **Source** | checklist |

**Steps to reproduce**
1. Log in as `company@test.com` (or `manager@test.com`), password `password123`.
2. Navigate to Finance → Taxes, or go directly to `/taxes`.

**Expected**: The Tax Settings page renders (list/manage tax rates).

**Actual**: The entire page body is replaced by the app's generic ErrorBoundary fallback: "Something went wrong. Please refresh the page." No tax UI renders at all.

**Evidence — console**
```
[ERROR] ReferenceError: usePage is not defined
    at ot (http://localhost:8000/build/assets/Index-CTuTIBtP.js:1:1681)
    ...
[ERROR] Error caught by ErrorBoundary: ReferenceError: usePage is not defined
```

**Suspected root cause**: `resources/js/pages/taxes/Index.tsx:17` calls `usePage().props` but the file never imports `usePage` from `@inertiajs/react` (only `PageTemplate` and `TaxSettings` are imported at the top). This throws on every render and is caught by the page-level ErrorBoundary, producing a fully blank page for the entire route.

**Fix**: Add `import { usePage } from '@inertiajs/react';` to `resources/js/pages/taxes/Index.tsx`.

## BUG-02 — Task/Project Start/Due Date and similar required fields aren't visually marked required (relies on native browser tooltip)

| | |
|---|---|
| **Severity / Priority** | ~~Major~~ **Minor** / P2 (downgraded — see correction below) |
| **Page / flow** | Projects → Tasks → Create Task (all roles that can create tasks: Owner, Manager, Member) |
| **Roles affected** | Owner, Manager, Member |
| **Source** | checklist (P0 CRUD pass) |

**Steps to reproduce**
1. Log in as `member@test.com` (or owner/manager).
2. Go to Tasks → Create Task.
3. Select a Project and enter a Title (the only two fields shown with a red `*`).
4. Leave Start Date and Due Date empty.
5. Click **Create**.

**Expected**: Start Date / Due Date should show the same red-asterisk required cue that Project/Title get.

**Actual**: Nothing visibly happens on click — no toast, no network request — and focus silently jumps to the Start Date field. Filling in both dates makes creation succeed immediately.

**CORRECTION (2026-08-23, second QA pass)**: originally reported as a fully silent dead-end. A follow-up pass on the equivalent Add Project dialog (same pattern: native `<input required>` with no visible asterisk) took a **screenshot** during the same empty-submit scenario and confirmed the browser's own native "Please fill out this field." tooltip **is** visible on-screen to a real user (see `project-create-empty-submit.png`) — the accessibility snapshot used for the original finding simply doesn't capture browser-native validation popups, which made it look silent when it isn't. The real, remaining defect is narrower: these fields are missing the same visible red-asterisk cue that Project/Title/Contract-form fields get elsewhere in the app, so a user has no advance warning before submitting, and has to rely on the browser's own tooltip after the fact. Downgraded from Major to Minor.

**Suspected root cause**: `resources/js/components/tasks/TaskFormModal.tsx` lines 260 and 272 render `<Label required>...Start Date/Due Date</Label>`, but the base `Label` component (`resources/js/components/ui/label.tsx`) does not accept or render a `required` prop/asterisk at all — it just spreads props onto the Radix primitive, which silently drops it (unlike Project/Title above them, which hardcode a literal `<span className="text-red-500">*</span>`).

**Fix**: Mark Start Date / Due Date with the same visible required-asterisk pattern used for Project/Title, or make the `Label` component actually render an asterisk when passed `required`.

## BUG-03 — Superadmin's own sidebar links to Media Library, which always 403s for superadmin

| | |
|---|---|
| **Severity / Priority** | Major / P1 |
| **Page / flow** | Superadmin nav → Media Library (`/media-library`) |
| **Roles affected** | Superadmin |
| **Source** | checklist |

**Steps to reproduce**
1. Log in as `superadmin@test.com`.
2. Click "Media Library" in the sidebar (Management group), or go directly to `/media-library`.

**Expected**: Either the nav item is not shown to superadmin at all, or the page loads.

**Actual**: `403 Forbidden` — "You don't have permission to access this page." every time, with no way to reach the page as superadmin.

**Evidence**: Reproduced twice (fresh navigation each time). Confirmed via `php artisan tinker` that the account genuinely holds the `media_view_any` Spatie permission (`hasPermissionTo('media_view_any') === true`), which is why the sidebar renders the link in the first place — the 403 is not a permission gap, it's a separate blocking middleware.

**Suspected root cause**: `routes/web.php:347-349` defines the `media-library` route inside a route group wrapped by the `block.superadmin.workspace` middleware alias → `App\Http\Middleware\BlockSuperAdminWorkspaceAccess`, whose entire body is `abort_if($request->user()?->type === 'superadmin', 403)`. Per that middleware's own doc comment, superadmin is intentionally barred from all workspace-scoped routes in that group (it has no `current_workspace_id`) and is meant to reach workspace data only via an Impersonate flow. However, `resources/js/components/app-sidebar.tsx`'s `getSuperAdminNavItems()` only checks `hasPermission(permissions, 'media_view_any')` — it has no awareness of this middleware — so it still renders a nav entry pointing at a route superadmin can never load. (`dashboard` explicitly opts out of this same middleware via `->withoutMiddleware('block.superadmin.workspace')`, confirming this is a known pattern the Media Library route was simply never given.)

**Fix**: Either remove "Media Library" from `getSuperAdminNavItems()`, or exempt the `media-library` route from `block.superadmin.workspace` the same way `dashboard` does (if superadmin is meant to browse a global media library rather than a workspace-scoped one).

## BUG-04 — Background timer-status polling keeps hitting the server after logout, throwing a console error every ~1s

| | |
|---|---|
| **Severity / Priority** | Minor / P2 |
| **Page / flow** | Any authenticated page with the timer widget active → Logout |
| **Roles affected** | All roles with `timesheet_use_timer` (Owner, Manager, Member) |
| **Source** | checklist (session/logout pass) |

**Steps to reproduce**
1. Log in as `company@test.com`.
2. Log out via the user menu.
3. Watch the browser console after the redirect to the landing page.

**Expected**: No further authenticated polling after logout.

**Actual**: Console repeats:
```
[ERROR] Failed to fetch timer status: SyntaxError: Unexpected token '<', "<!DOCTYPE "... is not valid JSON
```
The timer widget's polling interval is not torn down by the logout/navigation, so it keeps requesting `/timer/status`; since the session is gone, the server returns the login page's HTML instead of JSON, and the client's `JSON.parse` throws on every tick, indefinitely (until the page is closed or reloaded).

**Suspected root cause**: `resources/js/components/timesheets/TimerWidget.tsx` and `resources/js/components/timesheets/NavigationTimer.tsx` both poll `/timer/status`; the polling `setInterval`/effect does not appear to be cleared on the auth-state transition that logout causes.

**Fix**: Clear the polling interval on logout / when the authenticated user becomes null, and/or treat a non-JSON (HTML) response from `/timer/status` as "stop polling" rather than throwing.

## BUG-05 — Editing a project silently fails completely whenever Estimated Hours is 0 (the default value)

| | |
|---|---|
| **Severity / Priority** | **Major** / P0 |
| **Page / flow** | Projects → any project → Edit Project |
| **Roles affected** | Owner (root cause is server-side validation, affects any role with `project_update`) |
| **Source** | checklist (zone-based deep-dive, full create→verify→edit→delete journey) |

**Steps to reproduce**
1. Create or open any project whose Estimated Hours is 0 (the default — a new project's Estimated Hours field is optional and left blank/0 unless explicitly set).
2. Click **Edit Project**, change the Title (or any other field).
3. Leave **Estimated Hours** at 0 and click **Update**.
4. Observe: the dialog stays open, no toast/error appears anywhere.
5. Set Estimated Hours to any value ≥ 1 and click **Update** again — it now succeeds immediately, including the title change from step 2.

**Expected**: Either the update succeeds (Estimated Hours should be allowed to stay 0), or a clear validation message is shown explaining what's wrong.

**Actual**: The entire edit is silently discarded — not just Estimated Hours, but title/status/priority/dates too, since Laravel validates the whole request atomically and never reaches `Project::update()`. Verified directly against the database with `php artisan tinker`: after step 3, the project's title in the DB was still the pre-edit value despite the PUT request returning a 303 "success-style" redirect. No inline field error, no toast, nothing — the UI gives the user zero indication that anything went wrong.

**Root cause (confirmed)**: `app/Http/Controllers/ProjectController.php:456` (and the identical rule in `store()` at line 140): `'estimated_hours' => 'nullable|integer|min:1'`. `min:1` applies to any **present, non-null** value — `nullable` only exempts an actual `null`. The Edit form pre-fills the Estimated Hours input with the project's current value (`0` for any project that never had hours set), and submits that `0` explicitly, which fails `min:1`. This is why it doesn't reproduce on **Create**: an untouched Estimated Hours field there submits `null`/omitted rather than `0`, which passes `nullable` fine — the bug is specific to the **Edit** path, because it round-trips an already-stored `0`.

**Impact**: Since new projects commonly start with Estimated Hours unset (0), and there is no field-level indication of the problem, this will silently block edits to a large fraction of real projects the first time someone tries to change anything about them.

**Fix**: Change the validation rule to `'nullable|integer|min:0'` (0 is a legitimate "not estimated yet" value), and/or surface Inertia validation errors as inline messages or a toast in the Edit Project modal so a genuine validation failure is never silent.

## BUG-06 — "Create First Task" deep-link from a project's Tasks tab doesn't pre-select that project in the Create Task modal

| | |
|---|---|
| **Severity / Priority** | Minor / P2 |
| **Page / flow** | Project detail → Tasks tab (empty state) → "Create First Task" |
| **Roles affected** | Owner (and any role reaching this same code path — Manager, Member) |
| **Source** | checklist (zone-based deep-dive) |

**Steps to reproduce**
1. Open a project with no tasks yet, go to its **Tasks** tab.
2. Click **Create First Task**. This navigates to `/tasks?project_id=<id>&project_name=...`, correctly filtered/titled for that project.
3. Click **Create Task** on that filtered list.

**Expected**: The Project field in the Create Task dialog is pre-selected to the project just navigated from (the URL already carries `project_id`).

**Actual**: The Project dropdown shows the generic placeholder "Select a project" — the user has to manually re-select the exact project they just came from, defeating the point of the deep link.

**Root cause**: `resources/js/pages/tasks/Index.tsx:1089-1099` renders `<TaskFormModal>` without passing the current `selectedProject` (derived from the `project_id` query param) as a default. `TaskFormModal`'s own internal state (`resources/js/components/tasks/TaskFormModal.tsx:28-38`) only pre-fills `project_id` when editing an existing task (`task?.project_id`); the create path always starts at `''`.

**Fix**: Pass `selectedProject !== 'all' ? selectedProject : undefined` (or equivalent) into `TaskFormModal` as an initial-project prop, and have the modal seed `formData.project_id` from it when not editing.

## BUG-07 — A milestone created with no due date displays "Due: 1/1/1970" instead of "No due date"

| | |
|---|---|
| **Severity / Priority** | Minor / P2 |
| **Page / flow** | Project detail → Milestones tab → Add Milestone |
| **Roles affected** | Owner (and any role that can manage milestones) |
| **Source** | checklist (zone-based deep-dive) |

**Steps to reproduce**
1. Open a project → Milestones tab → Add Milestone.
2. Fill in only the Title (Due Date is optional and has no asterisk), submit.

**Expected**: The milestone card shows something like "No due date" when none was set.

**Actual**: The card shows "Due: 1/1/1970" — the Unix epoch, a classic symptom of formatting a `null`/missing date without a guard.

**Root cause**: `resources/js/pages/projects/Show.tsx:1325` — `Due: {new Date(milestone.due_date).toLocaleDateString()}` is called unconditionally; `new Date(null)` evaluates to the Unix epoch (Jan 1, 1970) rather than an "Invalid Date" that might at least be visually obvious.

**Fix**: Guard the render — e.g. `milestone.due_date ? new Date(milestone.due_date).toLocaleDateString() : t('No due date')`.

## BUG-08 — Submitting a timesheet with 0 entries silently fails with zero user feedback

| | |
|---|---|
| **Severity / Priority** | Major / P1 |
| **Page / flow** | Timesheets → Submit (on a draft timesheet with no entries) |
| **Roles affected** | Owner (root cause is server-side, affects any role with `timesheet_submit`) |
| **Source** | checklist (zone-based deep-dive) |

**Steps to reproduce**
1. Have a draft timesheet with 0 time entries (e.g. a newly-created empty week).
2. Click **Submit**.
3. Nothing visibly happens — no toast, no status change.
4. Confirm via DB the status is still `draft`.

**Expected**: A toast reading "Failed to submit timesheet" (the frontend code is already written to show exactly this).

**Actual**: Silent no-op. Confirmed by reading the live Inertia page props directly (`page.props.errors`) immediately after the click — it comes back as an empty `{}`, so the frontend's `onError` handler (which does correctly call `toast.error(...)`) never fires.

**Root cause**: Both ends of this look individually correct — `app/Http/Controllers/TimesheetController.php:575-577` correctly rejects with `return back()->withErrors(['message' => 'Cannot submit timesheet without entries']);`, and `resources/js/pages/timesheets/Index.tsx:125-136` correctly wires `router.post(...).onError(() => toast.error(...))`. The break is somewhere in how this specific redirect response is transported/interpreted by Inertia (the response came back as a plain `302` with `content-type: text/html`, not routed into Inertia's error-props flow) — pinning the exact line needs a framework-level trace (e.g. Laravel Debugbar) beyond what browser+DB verification alone can confirm.

**Fix**: Needs a developer to trace why `withErrors()` on this redirect isn't populating Inertia's shared `errors` prop — check the response status code Inertia expects for POST-redirect-back (303) vs what's actually being returned (302).

## BUG-09 — Invoices page "Overdue" widget and filter are effectively dead — never surface invoices that are actually overdue

| | |
|---|---|
| **Severity / Priority** | Major / P1 |
| **Page / flow** | Finance → Invoices |
| **Roles affected** | Owner (and any role with `invoice_view_any`) |
| **Source** | checklist (zone-based deep-dive, widget-vs-data cross-check) |

**Steps to reproduce**
1. Have any unpaid invoice (draft or sent) with a due date in the past.
2. Go to Invoices — the row correctly shows "X days overdue" in red under Due Date.
3. Note the "Overdue" stat card at the top reads 0.
4. Click the "Overdue" tab/filter — returns "No results found", even though the invoice is right there in "All Invoices".

**Expected**: Both the widget and the filter should count/show that invoice.

**Actual**: Both silently show/return nothing, permanently, for any invoice whose status hasn't been separately flipped to the literal string `'overdue'`.

**Root cause**: `app/Http/Controllers/InvoiceController.php:93,101` compute the Overdue count via `where('status', 'overdue')` — a literal DB column check. But nothing in the app ever proactively sets an invoice's status to `'overdue'`: `app/Models/Invoice.php:279-293` (`updatePaymentStatus()`) is the *only* code path that can set `status='overdue'`, and it only runs as a side-effect of `createPaymentRecord()` (i.e. an actual payment/webhook attempt) — never on a schedule or on page load. Meanwhile the model *also* has a correct `scopeOverdue()` (`Invoice.php:118-122`: `where('due_date','<',now())->whereNotIn('status',['paid','cancelled'])`) and a correct `getIsOverdueAttribute()` (used for the per-row "X days overdue" badge) — but `InvoiceController`'s own Overdue stat/tab uses neither. The correct pattern already exists elsewhere in this same codebase: `DashboardController.php:588` computes its own invoice-overdue widget via `where('due_date', '<', now())`, which is exactly why the Dashboard's own Overdue widget validated correctly earlier in this QA pass.

**Fix**: Change `InvoiceController.php:93` and `:101` to use the existing `scopeOverdue()` (i.e. `(clone $query)->overdue()->count()`) instead of `where('status', 'overdue')`, matching what `DashboardController` already does correctly.

## BUG-10 — Budget page throws a 500 error on every load

| | |
|---|---|
| **Severity / Priority** | **Major** / P0 |
| **Page / flow** | Finance → Budgets |
| **Roles affected** | Owner (and any role with `budget_view_any`) |
| **Source** | checklist (zone-based deep-dive) |

**Steps to reproduce**
1. Log in as any role with `budget_view_any`.
2. Navigate to Finance → Budgets.
3. Open the browser console — `GET /budgets/default-categories` returns `500 Internal Server Error` every time the page loads (this endpoint fires automatically, not on a user action).

**Expected**: No server error; the page's default-category data (presumably feeding a picker shown when creating/editing a budget) should load normally.

**Actual**: 500 error every single page load.

**Root cause (confirmed)**: `app/Http/Controllers/ProjectBudgetController.php:328` unconditionally reads `$category['id']` while mapping over `BudgetCategorySeeder::getDefaultCategories()` (`database/seeders/BudgetCategorySeeder.php:61-75`), whose array items only have `name`/`color`/`description`/`sort_order` keys — there is no `id` key at all. Confirmed via `storage/logs/laravel.log`: `Undefined array key "id"` at that exact line, and this has reproduced for **two different users on two different dates** (a prior session's user on 2026-08-22, and this session's owner account on 2026-08-23) — a pre-existing, consistently-reproducible defect, not something this QA pass caused.

**Fix**: Add a stable `id` (e.g. array index + 1, or a slug) to each item in `BudgetCategorySeeder::getDefaultCategories()`, or change `ProjectBudgetController.php:328` to derive an id instead of assuming one exists.
